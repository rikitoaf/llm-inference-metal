## 1. Tencent DSpine

Sources: https://github.com/Tencent/DSpine (README, `dspine_mlx/`, `sglang_dspine/`, `docs/sps_tuning.md`),
paper arXiv 2609.36173 v2, model card https://huggingface.co/tencent/Qwen3.8-27B-DSpine-b16, video
https://www.youtube.com/watch?v=3lgQyTOHtIw (metadata and description only; no transcript was retrievable).

### 1.1 What it is [V]

DSpine is a DFlash-family block drafter. Same skeleton as our DFlash2: 5 Qwen3 decoder layers, hidden 5120, target
hidden states from 5 layers concatenated → `fc` (25600 → 5120) → per-layer context K/V, an anchor + mask-token block,
and the target's own (frozen) vocabulary head. What it changes:

1. **Block-causal attention inside the block.** Row t sees the context plus rows 0..t. (DFlash/DFlash2 attend
   bidirectionally inside the block; our DFlash2 config has `is_causal: false`.)
2. **"Adjacent Causal Injection" ("condition through depth"):** after every layer, each row receives a gated message
   computed from its *predecessor's* features before that layer's update: normalize → project to a 1024-d code →
   gate `σ(G_q z_t + G_p z_{t-1})` and message `A z_{t-1}` (rank 512) → write back `h_t = u_t + RMS(u_t)·W_ℓ m_t`.
   All rows still compute in parallel, but each position now knows what the previous position is likely to be. The
   anchor row uses a fixed codebook entry (PCA-whitened LM-head rows, 248,320 × 1024).
3. **Last-write refinement:** for each position and each of the 16 predecessor candidates, the last layer's write is
   redone with that candidate's code, giving an exact **16 × 16 conditional logit table per position**. The paper's
   ablation: dropping refinement costs 6.6-7.1% of acceptance length; dropping refinement and injection 8.8-10.7%.
4. Verification in their SGLang server is a chain with standard rejection sampling. "DSpark dynamic verification /
   SPS" picks a fixed verify width per batch size offline (for one stream this is just a width choice, like our
   idea E4). "ReplaySSM" is GDN replay of the accepted prefix, which Splash already does (for trees too).

### 1.2 The 27B checkpoint [V, ✔]

`tencent/Qwen3.8-27B-DSpine-b16`, created 2026-11-07, Apache-2.0, not gated: one BF16 safetensors file of 4.05 GB,
2.03 B parameters (embedding and head come from the target). ✔ Config: 5 layers, hidden 5120, `block_size` 16,
`dflash_config.draft_block_causal: true`, sliding window **8192** (ours: 2048), `target_layer_ids` **[1, 16, 31, 46,
61]** (ours: [5, 19, 33, 47, 61]), code bridge 1024 / rank 512, refinement top-16.

✔ **The card's baseline is exactly our drafter:** `z-lab/Qwen3.8-27B-DFlash2` and `incoai/Qwen3.8-27B-DFlash2` (which
Splash uses) have the same safetensors sha256 (`67fc76d68dc5…`).

Claimed acceptance length (SGLang, BF16 target, concurrency 8, CUDA GPU not named; **DSpine at block 16 with SPS vs
DFlash2 as an 8-token chain**):

| Benchmark | DFlash2 T=0 | DSpine T=0 | DFlash2 T=1 | DSpine T=1 |
|---|---|---|---|---|
| GSM8K | 5.69 | 7.20 | 5.45 | 6.31 |
| MATH-500 | 5.49 | 6.49 | 5.27 | 5.66 |
| HumanEval | 4.87 | 5.71 | 4.34 | 4.71 |
| MBPP | 5.04 | 6.14 | 4.79 | 5.41 |
| MT-Bench | 4.11 | 4.48 | 3.89 | 4.03 |

Agent benchmarks (T=1): DFlash2 3.95-4.70 → DSpine 4.77-5.63 (+14-33%); end-to-end agent throughput DSpine/DFlash2
**+8-21%**, DSpine/autoregressive 2.71-3.84×.

At **equal block size** (Qwen3-8B) the gain is much smaller: +3.7% (T=0) / +6.9% (T=1) with equally trained drafters
(README), +9.8% in the paper's ShareGPT table. So most of the 27B card's gain is the 16-deep block vs DFlash2's 8.

### 1.3 The video's "4× faster" [V]

Channel "Codedigipt", uploaded 2026-11-07, 11 minutes; the description restates the model card ("up to 3.84× higher
throughput in agent-based workloads"). **3.84× is against plain autoregressive decoding** on a CUDA server at
concurrency 8 (the best single cell). Against DFlash2, the drafter we already run, the same table says 1.08-1.21×,
and that is confounded by block 16 vs 8. For us the honest question is "DSpine vs DFlash2 inside our existing tree +
copy", not 4×.

### 1.4 What it would give us [E]

Our stack already has what DSpine's numbers partly measure: a 16-row verify with a best-first tree (+23.5% over the
chain) and a copy extension to depth 15. Also, our tree draws deterministic proposals (q = 0), so DSpine's better q
for rejection sampling does not apply.

- **Phase 1, DSpine at 8 draft rows inside today's tree + copy + shortlist:** block-causal attention and
  predecessor-only messages mean rows 0-7 of a 16-row block are exactly what an 8-row run computes, so this is
  legitimate (their MLX README runs `--block-size 8`). Expected **+2-6% tokens/cycle** (central +4%).
- **Phase 2, 16 native draft rows** (our idea E10, now with a drafter actually trained at 16): another **+3-8%**,
  overlapping the copy extension (which already fills depth 8-15 in ~32% of cycles).
- **Cost per cycle:** backbone slightly cheaper than DFlash2 (no dynamic convolutions), bridge + refinement add
  ~30 small dispatches: net **+0.2-0.8 ms** on ~87 ms (break-even ≈ +1% tokens/cycle). The 8192 window adds
  ~0.5-1 ms at long context. Phase 2's 16 draft rows: +1.5-3 ms.
- **Memory:** ~1.5-1.6 GB stored the way Splash stores DFlash2 (Q4 backbone, bf16 codebook) vs 1.27 GB: **+0.25-0.3 GB**
  (≈ 16-18K tokens of context). Draft ring at the trained 8192 window: +126 MB. Don't keep both drafters resident
  (+1.5 GB); switch by restart.
- **Net expectation:** +3-10% decode, central ~+5%; probability phase 1 clears noise ~50-60%.

**Fit with Splash is unusually good [V]:** same backbone shapes and context mechanism (`addContextPrefill` /
`addContextCommit` reusable), and the refinement's 16 × 16 table is the same shape `draft_select_tree` already consumes
(`score = unary + tables[from][j]`), so the tree, the copy extension, the shortlist, acceptance and the commits stay.

**`dspine_mlx` as a separate backend is not feasible [V]:** it supports pure-attention Qwen3 targets only ("the current
MLX port supports pure-KV Qwen3-8B only"); our target's GDN layers are unsupported, and an MLX 4-bit 27B (~15 GB) plus
a 4 GB bf16 draft does not fit next to macOS in 24 GB.

### 1.5 Plan: a selectable drafter module (`SPLASH_DRAFTER=dflash2|dspine`, DFlash2 stays the default)

| Phase | Work | Gate |

| 3. Tuning rounds, later (user, 2026-11-09: "spend more time to modify and compare again") | after the first A/B, tune one knob at a time and rerun the same A/B; list below | each round: same prompts, seeds and A-B-B-A order as round 1, so results stay comparable; the eval only for the final candidate |

**Phase 3 tuning knobs, roughly by expected value:**
1. Tree budget for DSpine: node count (12/16/20), and the depth-versus-width split. Its 16×16 tables are sharper
   than DFlash2's, so a deeper, narrower tree may win.
2. Copy-row competition: how many rows the copy extension takes from DSpine, since the two may predict the same
   tokens.
3. Acceptance calibration: refit the table → acceptance-probability mapping on DSpine's own accept logs. This is
   the same recalibration still pending for the copy extension.
4. Context window, 2048 vs 8192: accuracy against draft attention cost at long context.
5. Precision: backbone Q4 vs Q6/Q8; bridge bf16 vs Q8. Memory against acceptance.
6. Shortlist size for the refinement gather (cost against tail misses).
7. A context-dependent policy: pick the drafter or row count by context length, if DSpine wins short but loses
   past 64K, where verify rows cost more (ANALYSIS.md section 5).

**Comparability rules:** keep round 1's raw per-prompt numbers in `splash/dev-dspine/DSPINE-PORT.md` as the fixed
baseline, and log every round as a table row: knob, value, tokens/cycle, ms/cycle short and long, Δ against DFlash2.
Rerun the DFlash2 arm in each round as well, since thermal state and OS updates drift.

## 2. billion-context

Source read at commit `848f59b` (v0.1.213): https://github.com/ranxianglei/billion-context, its paper and docs.

### 2.1 How it works [V]

- A local HTTP proxy rewrites each outbound request. Every message gets a ref tag (`<acp tokens="2.1K"
  type="tool:bash">m00175</acp>`); the model is given four tools (`compress`, `decompress`, `search_context`,
  `acp_status`) and a ~3K-token "doctrine" in the system prompt.
- **The model itself writes the summaries**, as the argument of a `compress` call, when the proxy nudges it
  (✔ defaults: context ≥ 45% of the window **and** 50,000 tokens of growth since the last fold; forced at 75%;
  emergency truncation at 95%).
- A fold drops the covered messages from the outbound request and puts the summary at the earliest covered position;
  the client's own history is untouched. Bytes before the fold point stay identical (their rule I2), so the cache
  only misses from the fold onward.
- **The dsh plugin exists** (`src/agent/dsh-native.ts`): it spawns the proxy, **patches the process-wide `fetch`** to
  route `/chat/completions` through it, registers the four tools as native dsh tools, and turns dsh's own compaction
  off. It works with a local endpoint and no API key. No hook collisions with our runaway or purpose-effort plugins.

### 2.2 Fit [E, built on V inputs]

- **Today's baseline already sawtooths** between ~21K and ~104K (dsh compaction at 0.8 × 129,520, keep 16% ✔). Mean
  decode across that band ≈ 40 tok/s.
- **bili with defaults** would sit around 25-80K: about the same band, so **little or no decode gain**. Their own
  pilot on qwen3.8-27b (64K window): mean context 21.0K vs 26.5K (−21%); an extreme setting reached 13.7K but had
  the worst quality (75.7% probes, 3 execution errors vs 81.6% and 1).
- **Tuned to ≤ ~45K** it could save ~20 s per step (decode ~41 → ~58 tok/s), minus ~1-2 min per fold (an xhigh
  compress step plus a 6-12K re-prefill), amortizing to **~20-25% faster, only in sessions past ~50K**. In t1-t6
  (small contexts) it would never fold: pure overhead (~3-4K extra prefix tokens).
- **"5× fewer tokens"** is their counterfactual for a 1M-token window; for 200K windows the paper predicts 1.2-1.8×.

### 2.3 Risks [V unless marked]

1. **A 3-bit 27B writing correct compress calls.** Their own pilot on the same model family (full precision, T=0)
   completed 5/8 compressions at default tuning and 17/38 at extreme, and "spontaneous tool adoption is zero at this
   model scale". Ours is a 3-bit quant [E: worse].
2. **Splash's prefix cache on a hybrid model** can resume only from a published state at or before the fold point;
   if those states were evicted (low RAM), the fallback is a 30-45K re-prefill (1.5-2.5 min) [E].
3. **Compress steps run at xhigh**: they carry no purpose, so our purpose-effort plugin cannot turn their thinking off.
4. **Coding needs exact paths, signatures and error strings**, which summaries may lose [E].
5. **Maturity and security:** MIT; ~185K lines of fast-moving, largely agent-written TypeScript; recent bugs included
   one that folded another session's messages (#5196) and 10 s main-thread stalls (#5337). **Auto-update is on by
   default** (checks npm every 3 minutes and installs over itself; an advisory watcher force-installs pinned versions
   even with auto-update off unless `BILI_ADVISORY_CHECK=0`). The proxy has no authentication, stores all
   conversation content, and the dsh plugin relays its admin API through dsh's web server.

### 2.4 Verdict and what was done

Don't adopt it now. Its speed comes from smaller context, which dsh's mature compaction can give by firing earlier;
its distinctive value (incremental, reversible folds that only rewrite the tail) depends on the 27B making reliable
compress calls, which the authors' own data on this model family puts in doubt.

**Added (modular, off by default):** `config/dsh/shortctx.cordis.patch.yml`, applied when `DSH_SHORT_CONTEXT=1`
(`scripts/dsh-env.sh`): compaction at 37% of the window (~48K) keeping 12K tokens. Verified to compose
(`--dump-config`); unmeasured. Measure it on a long session: per-step decode tok/s by context, compaction count and
time (thinking is already off for compaction), hidden pass rate, recall of early facts.

**If a trial of bili is ever wanted:** pinned install outside the repo (`npm install --ignore-scripts` of a reviewed
v0.1.213), `ACP_AUTO_UPDATE=0 BILI_ADVISORY_CHECK=0 BILI_SQLITE_AUTO_DOWNLOAD=0`, a `billion.cordis.patch.yml` toggle,
`maxContextLimit 48000`, `nudgeGrowthTokens 15000`, `promptPack lean`, and compare against `DSH_SHORT_CONTEXT=1`, not
against today's default. Kill if compress success < 60%, t1-t6 pass drops > 3 points, or it isn't ≥ 10% faster than
the short-context arm on a >100K session.

## 3. codebase-memory-mcp (DeusData), added 2026-11-09

Source read at commit `612eee2` (2026-11-05), MIT. Built from source and trialled the same day (section 3.5); the
sections 3.1-3.4 below are the pre-trial analysis.

### 3.1 What it is [V]
- **One native C binary, no runtime dependencies.** It indexes a repo with 162 vendored tree-sitter grammars plus
  "Hybrid LSP" type resolution, into a SQLite knowledge graph under `~/.cache/codebase-memory-mcp/`.
- **Graph contents:** functions, calls, imports, routes, docs, Docker/Kubernetes/Terraform.
- **17 MCP tools:** `search_graph` (structural + BM25 + semantic, with nomic-embed-code embeddings built in),
  `trace_path` (callers and callees to depth 15), `get_code_snippet`, `get_file_outline`, `get_architecture`,
  `detect_changes`, `query_graph` (Cypher), and others.
- **Speed (their M3 Pro numbers):** Django indexes in about 6 s; a query takes under 10 ms.
- **Claimed benefit (their preprint, frontier agents, 31 repos):** 10× fewer tokens and 2.1× fewer tool calls
  than reading file by file.
- **Built-in tool profiles:** `--tool-profile=scout` (8 tools) and `analysis` (13), so no filter proxy is needed,
  unlike xerj.
- **Privacy:** it makes no network calls on its own (no update check, no phone-home); the optional Lens UI
  downloads a browser model only when asked.
- **Installer is invasive:** by default it writes MCP config, skills, agent profiles and hooks into every coding
  client it detects. For us: `--skip-config`, or `install --no-hooks`, then a manual dsh entry.
- **Shared daemon:** one per account, with watchers that re-index on change.
- **Limits available:** `CBM_MEM_BUDGET_MB`, `index_max_rss_mb`, `CBM_ALLOWED_ROOT`, `auto_watch`.

### 3.2 Fit for this stack: measured inputs
**Our tool traffic** (`splash/tools/session_tool_share.py`, all 78 dsh sessions):
- Tool results total 1.60M chars (~400K tokens).
- **89% of that is code navigation:**
  - `read`: 224 calls, 1.0M chars;
  - navigation shell commands (grep/find/cat/sed): 0.30M;
  - `grep`: 64K;
  - xerj: about 60K.
- Only 16 of 224 reads repeat a path.
- For scale, reasoning is 3.16M chars. Decode dominates agent time (ANALYSIS.md section 7), so tool results are
  the minor part of context.

**Schema cost** (measured from `src/mcp/mcp.c` string literals):
- all 17 tools: about 20.8K chars (~5.2K tokens);
- scout: about 9.3K chars (~2.3K tokens);
- xerj's filtered set, for comparison: 23K chars.
- The schemas sit in every request: prefix-cached, but they occupy context. At 0.45 ms per 1K tokens per
  cycle (ANALYSIS.md section 5), scout costs about 1 ms per cycle, roughly 1% decode, always on.

**Where a gain could come from:**
1. Fewer and smaller reads, so shorter context, so faster ms/cycle and less prefill.
2. Fewer agent steps for "where is X / who calls X" questions. Each step saved is a full reasoning decode, the
   expensive part.

Point 2 is the real lever, but only if the 3-bit 27B picks the graph tools instead of reading. Our xerj experience
(memory: "the agent barely used xerj on real work") says that is not given.

**RAM** [E]:
- The index is on disk.
- Indexing peaks in RAM (RAM-first pipeline); cap it with `CBM_MEM_BUDGET_MB`.
- The daemon's idle RSS must be measured. Splash needs every GB: low free RAM evicts prefix states.

### 3.3 Verdict (before the trial; the measured verdict is in 3.6)
**Worth a measured, opt-in trial; not a default.** Compared with xerj it is lighter: no search node, a smaller
scout schema, profiles built in, no telemetry. It also adds call-graph and impact tools that xerj lacks. The risks
are tool adoption by a 3-bit model, the always-on schema cost, and the invasive installer.

**Config (global, in `~/.cache/codebase-memory-mcp/_config.db`):** `auto_index false`, `auto_watch false`,
