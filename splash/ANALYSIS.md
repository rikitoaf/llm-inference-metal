# Splash + dsh: performance analysis and adaptation guide

Last revised 2026-11-09. This document explains why the local stack runs at the speed it does, what every speed
experiment so far found, what is left, and how to judge a new technique (a new drafter, model, quantization, chip or
harness feature) before spending GPU time on it. The raw measurements live in [SPEED_LOG.md](SPEED_LOG.md); the older
plans are in [SPEED_PLAN.md](SPEED_PLAN.md) and [RESEARCH-ADVANCED-2026-11-02.md](RESEARCH-ADVANCED-2026-11-02.md).
This file is the synthesis: start here.

Labels used throughout:
- **measured**: a number from a logged GPU run (the log is named).
- **derived**: arithmetic from measured numbers and the model's shapes (the arithmetic is shown).
- **estimate**: a judgement or a simulation; treat it as a hypothesis until a GPU run confirms it.

## 1. The system in one page

```
 you ──> dsh (agent harness, Node)            plugins: runaway guard, purpose-effort, guidelines, (JEV off)
          │  OpenAI-compatible HTTP, one request per agent step, the whole conversation each time
          ▼
        Splash server (Python front end, localhost:8000)  ──  prefix cache (RAM + SSD tier, persistent)
          │
          ▼
        Splash runtime (C++/Objective-C++, Metal)  ──  one command buffer per decode cycle, ~700 dispatches
          │
          ▼
        M5 Pro GPU: 16 cores, ~307 GB/s unified memory, ~25 TFLOP/s FP16 matrix units (measured), 24 GB total
```

**Target model: Qwen3.8-27B, GGUF UD-IQ3_XXS** (Unsloth dynamic quant, ~2.8-3 bits per weight).
- 64 layers: **48 Gated DeltaNet** (linear attention with a fixed-size recurrent state) and **16 full attention**
  (every 4th layer). Hidden size 5120, attention 24 query heads / 4 KV heads (GQA ratio 6), head dim 256, vocabulary
  248,320.
- Only the 16 attention layers have a KV cache. The GDN layers carry ~150 MiB of recurrent state per sequence, which
  cannot be rolled back to an arbitrary position (this is why prefix caching snapshots states at fixed points).
- Weights streamed per verify pass: **10.66 GB** (IQ3_S 3.07, IQ3_XXS 2.99, IQ2_* 1.60, IQ4_XS 1.44, Q4_K 0.94 of which
  0.72 is the output head).

**Draft model: DFlash2, block 8.** A 5-layer Qwen3-style block drafter (hidden 5120, 32/8 heads, head dim 128, FFN
17408, sliding window 2048) conditioned on hidden states captured from the target. It proposes a block of 7 tokens
after the anchor in one parallel pass, plus per-position top-K candidates and edge scores. Weights streamed per cycle:
**1.27 GB**, plus its own pass over the vocabulary head (now shortlisted).

**KV cache: turbo-int4** (default since 2026-10-06). Keys and values rotated by a randomized 256-point Hadamard
transform, then int4 with a least-squares scale; the GPU's matrix units read the 4-bit pages directly.
**16.5 KiB per token** for all 16 layers (one 32-token page is 528 KiB). Needle retrieval matches INT8 to 82K and
finds needles out to 180K (TURBOQUANT.md).

**Harness: dsh** (DeepSeek Harness). Each agent step sends the full conversation; the server's prefix cache makes
that cheap as long as the rendered prompt is byte-stable (stable system prompt, `preserve_thinking`). Context window
in dsh = server limit − 20,480 (generated by `scripts/dsh-env.sh`).

**Production speculation stack (all exact, all on by default):** 16-row verify, 16-node best-first draft tree,
draft-head vocabulary shortlist, copy extension to depth 15. Section 4 explains each.

## 2. The speed equation

Everything in this document moves one of four terms:

```
decode tok/s  =  tokens accepted per cycle  /  seconds per cycle

agent wall time  ≈  Σ_steps [ decoded tokens / decode tok/s ]          (≈ 60-93% of wall, see §7)
                 +  Σ_steps [ uncached prompt tokens / prefill tok/s ]  (≈ 6-20%)
                 +  tool execution + approvals                          (≈ 10%)
                 +  compaction (a decode + a cold prefill)              (≈ 0-10% per long session)
```

- **Tokens per cycle** is set by the speculation: how many of the drafted tokens the target accepts each cycle (plus
  the one "bonus" token the target always produces). It depends on the text (code and copied text are easy, fresh
  reasoning is hard), the temperature and the drafter.
- **Seconds per cycle** is the cost of one target verify pass over 16 rows plus the draft, sampling and commits. It
  depends on weight bytes, kernel efficiency and context length.
- The two multiply. A +10% tokens/cycle change and a −10% ms/cycle change compound to +22%.
- **How many tokens** the agent decodes is the third, often biggest, lever: reasoning effort, runaway replies, and
  how often the harness re-sends or re-summarises context.

Worked example, today's production at short context (measured, eval 2026-11-03, `logs/splash/steps.jsonl`):
5.46 tokens/cycle / 87.4 ms = **62 tok/s**. At ~100K context: 4.11 / 132.9 ms = **31 tok/s** (section 5).

## 3. Anatomy of one decode cycle

### 3.1 The budget (1 lane, 2K context; measured with decode-profile, before E3 and the K-split)

| Part | ms | Share |
|---|---:|---:|
| GGUF verify projections, 64 layers, 16 rows | ~67.6 | ~80% |
| ↳ grid formats IQ3_S + IQ3_XXS + IQ2_* (7.66 of 10.66 GB) | ~48 | |
| ↳ IQ4_XS | ~10 | |
| Draft model (5 layers, 1.27 GB, ~231 GB/s) | ~5.5 | 6.5% |
| Output head (shortlisted) | ~1.5 | 2% |
| GDN tree scan + commit | 2.4 + 1.2 | 4.3% |
| Norms, attention at 2K, selection, glue | ~1.8 | 2% |
| Host gap between cycles | 0.63 | 0.7% |

Today (after E3 −2.0% and the K-split −0.9%, copy +0.3 ms) the same cycle is ~82-86 ms in decode-profile and
~87 ms in real sessions at short context.

### 3.2 The floors, and why the cycle sits at twice the bandwidth floor

- **Bandwidth floor** (derived): 10.66 GB / 307 GB/s = 34.7 ms for the verify weights.
- **Matrix-unit floor** (derived): 26.6e9 weights × 16 rows × 2 FLOP = 0.85 TFLOP per cycle; at the measured
  ~25 TFLOP/s FP16 rate that is ~34 ms. The `diag-nodeq` kernel (no dequantization) already runs at that rate:
  2.85 GFLOP in 0.113 ms for a 17408×5120 projection (measured, SPEED_LOG 2026-10-21).
- **What the measurements showed** (SPEED_LOG "why a decode projection takes 0.22 ms"): one projection costs the
  matmul (~0.11 ms) **plus** the dequantization (~0.08-0.11 ms), **in series**. They compete for the same issue slots
  of a GPU core; neither more simdgroups nor double-buffered operands made them overlap. DRAM loads are only ~8% of
  the time (cache-hot weights: 0.206 vs 0.225 ms).
- **Consequences** (these drive every later decision):
  1. The weight format barely matters for speed (Q4_K is only ~5% faster than IQ3_XXS per projection), so a bigger,
     better-quality quant is not much slower per cycle; it costs memory, not time.
  2. **16 verify rows cost the same as 8** in every projection (MPP fragments are 16 rows anyway). Verifying more
     candidate tokens per cycle is nearly free. That is why the draft tree and the copy extension paid off.
  3. The only exact ways to make projections cheaper are fewer instructions per weight in the dequant (E3 got ~2%,
     the ceiling is ~+10%), or a faster matmul type (int8/e4m3 matrix units, unprobed on M5).
  4. Host-side tricks (pipelining, sliced submission) are capped at the 0.63 ms host gap: dropped.

### 3.3 Where M5-specific behaviour showed up

- The 16-row staged tile at one lane (`m16-one-lane`) beat the 32-row tile: −2.9% per cycle.
- K-split policy: the long-K down projection (5120×17408) runs faster split 4 ways on 16 cores (−0.9% per cycle).
  The tier table is per core count, so a chip with a different core count needs its own sweep (§12.4).
- Constant-memory grid tables indexed per lane, and threadgroup copies of them, were slower (A1 +7.3%); fp16 copies of
  the grid in constant memory were faster (E3 −2%). The compiler already folds sign decoding (XOR variants +11-15%).

## 4. Tokens per cycle: speculative decoding

### 4.1 How a cycle works

1. **Draft**: DFlash2 reads the target's captured hidden states and proposes, for each of 7 positions after the
   anchor, a ranked list of candidate tokens with unary scores and edge (transition) scores.
2. **Tree build** (`draft_select_tree`, GPU): best-first search over those scores picks the 15 most probable nodes
   (path probability = product of per-step softmaxes). Row order is pop order. Each row gets a parent, a depth and an
   ancestor bitmask.
3. **Copy extension** (`draft_copy_extend`, GPU): the tree's most probable depth-7 path (8 tokens with the anchor) is
   matched against the request's own history (prompt + output). If an earlier occurrence matches ≥3 tokens, the tokens
   that followed it are chained at depths 8-15, replacing the tree's least probable rows while their calibrated
   acceptance prior beats the row they replace.
4. **Verify**: the target runs all 16 rows in one pass. Attention masks keys by the ancestor bits; the GDN layers scan
   the tree (each node starts from its parent's state).
5. **Accept**: walk from the anchor; at each node the target draws its token (argmax at T=0, a plain draw from p at
   T>0, with an independent uniform per depth); if a child holds that token, descend; otherwise that draw is the
   correction token. This is **exact sampling**: the output distribution equals the target's own.
6. **Commit**: KV rows of the accepted path are re-stored in depth order, the GDN state is replayed along the path,
   the draft's context is committed, and the next cycle starts at the new anchor.

### 4.2 What each layer of the stack bought (measured)

| Stage | Agent-like prompts | Note |
|---|---|---|
| Chain of 7 (DFlash2 alone, 8 rows) | 3.68 tok/cycle, 41.7 tok/s | greedy, thinking on |
| + 8-node tree in the same 8 rows | 4.04, 45.3 (+8.6%) | 2026-10-21 |
| + 16 rows, 16-node tree | 4.46, 51.5 (+23.5% over chain) | 2026-10-21 |
| + draft-head shortlist | 52.8 tok/s (+2.6%) | cheaper draft, same acceptance |
| + copy extension (real dsh session prompts, T=0.6) | 4.97 → 5.80 (+16.7%) | 2026-11-03; +4% in the real eval |
| Real eval, production today | 5.46-5.51 at <32K, 4.1-5.0 at 48-112K | 2026-11-03 |

Sampling settings (2026-10-21): T=0.6 (Qwen's recommendation; dsh sends no temperature, so Splash's default rules)
gives +6% tokens/cycle over T=1.0. `SPLASH_DRAFT_TEMPERATURE_SCALE` is inert since the tree (the tree takes the draft's
argmax path; q = 0).

### 4.3 What limits tokens per cycle now

- **Depth.** DFlash2 drafts 7 positions. 20% of greedy agent cycles and 49% of T=0.6 code cycles accepted all 7
  (measured, 2026-11-02); 32% in the eval. The copy extension is the only source of depth 8-15; it fires in ~32% of
  cycles and accepts past depth 7 in ~11% (real eval).
- **Selection.** With a perfect choice among DFlash's top-16 candidates per position, tokens/cycle would be 5.91 vs
  the tree's 4.45 (+33%, derived from the draft dump). The tree's scoring, not the candidate list, leaves that gap.
  Learned selectors (Weaver/DFlash-TfM, +32% claimed) or a better drafter (DSpine, §13) attack exactly this.
- **Text type.** Fresh reasoning is the hardest text: the agent's output is ~96% reasoning characters (2026-11-04
  transcript analysis). Copy helps where the model reproduces code it drafted while thinking (tool-call arguments,
  edits).
- **Context.** At 48-112K the real eval accepted 4.1-5.0 vs 5.5 at short context. Two candidate causes, not yet
  separated: the drafter's 2,048-token sliding window sees less of a long context; and long sessions are at a later,
  harder stage of the task. A fixed-prompt A/B at 2K vs 64K (same continuation) would separate them.

### 4.4 Rules of thumb (derived from the dumps and A/Bs)

- One more accepted token per cycle at ~5.5 tokens is worth ~+18% decode speed; it costs nothing extra as long as the
  rows fit in 16.
- Tree nodes 9-16 added only +12% tokens/cycle over 8 nodes (3.975 → 4.45). Rows past 16 lose: a 24/32-row tile costs
  ×1.38-1.40 per cycle for +5-7% tokens.
- Scaling the draft's scores before the tree build only hurts (the draft is calibrated).

## 5. Long context: why speed halves at 100K

### 5.1 What a real session sees (measured, 2026-11-03, `logs/splash/steps.jsonl`, production with copy)

| Context | Cycles | Tokens/cycle | ms/cycle | tok/s |
|---|---:|---:|---:|---:|
| 0-16K | 15,426 | 5.46 | 87.4 | 62.4 |
| 16-32K | 13,169 | 5.51 | 90.8 | 60.7 |
| 48-64K | 1,856 | 4.36 | 117.5 | 37.1 |
| 64-80K | 8,281 | 4.55 | 124.6 | 36.5 |
| 80-96K | 4,212 | 5.01 | 128.9 | 38.9 |
| 96-112K | 4,051 | 4.11 | 132.9 | 30.9 |

Cycle time grows roughly linearly: **ms ≈ 87 + 0.45 × (context in K tokens)** in real sessions (decode-profile on a
synthetic prompt: +0.34 ms per 1K). The extra time is entirely the 16 verify-attention layers; nothing else in the
cycle depends on context (the draft uses a 2,048-token window).

### 5.2 Why: verify attention at long context is compute-bound, not bandwidth-bound (derived)

Per 1K tokens of context, per cycle:
- **KV bytes read**: 1,000 × 16.5 KiB = 16.9 MB, read twice (the lane's 16 rows run as two 8-row tiles) = 33.8 MB.
  At 307 GB/s that is **0.11 ms**.
- **Matrix work**: 16 rows × 24 query heads × (256 for Q·K + 256 for P·V) × 2 FLOP × 16 layers × 1,000 tokens =
  **6.3 GFLOP**, which at the measured ~25 TFLOP/s FP16 rate is **0.25 ms**, before softmax and dequant ALU work.
- **Measured**: 0.34 ms (decode-profile) to 0.45 ms (real sessions) per 1K.

So the attention kernels are working at roughly 55-75% of the matrix-unit peak; memory is not the limit. This explains
two earlier results that looked puzzling:
- The single 16-row tile (read the KV once instead of twice) was **slower** at 32-64K (+2.8% / +9.6%): it saved
  bandwidth that was not the bottleneck and halved the threadgroups in flight.
- Changing the split size (pages per split) did nothing.

It also says what will work: **less attention math per cycle**. Each verify row costs 1/16 of the attention term, and
the GQA layout means every KV page is multiplied against 6 query heads × 16 rows.

### 5.3 The options, ordered by safety

| Option | Exactness | Expected effect at 100K | Notes |
|---|---|---|---|
| **Per-cycle verify rows** (E4): at long context, verify 8 rows when nodes 9-16 are improbable | exact | simulated +5.4% at 96K, +8.9% at 128K | halves attention math in those cycles; costs the +12% tokens rows 9-16 bring. A context threshold plus a probability threshold |
| **Keep the context short** (harness side): compaction earlier, context compression (billion-context, §13), smaller tool results | approximate (task state lives in summaries) | 31 → ~55-60 tok/s if a session stays under 32K | the largest lever on this curve; risk is the 27B's summary quality |
| **int8 Q·K** in verify attention | exact-math or approximate | 3-10% at long context (estimate) | needs a probe of M5's int8 matmul rate first |
| **Page-selective (Quest-style) attention**: attend only to the top-scoring KV pages | approximate | +11% at 58K, +27% at 131K (estimate) | costs needle accuracy; last resort |
| A faster softmax / fewer barriers in the turbo-int4 tile | exact | small (the matmul share dominates) | |

### 5.4 Prefill also slows with context

Prefill ≈ 1.2 s + uncached tokens × (2.22 ms + 0.024 ms per 1K of context): ~326 tok/s below 20K, ~175 tok/s at
120-140K (measured from session logs, 2026-10-27). Attention is 7% of a cold 16K prefill, 24% at 58K, 49% at 180K.

## 6. Prefill and the prefix cache

- Prefill runs near the FP16 compute peak (~22 TFLOP/s on the linear layers, 84-90%). It is not a kernel-efficiency
  problem; the lever is **not prefilling** (cache hits).
- The prefix cache served 90% of prompt tokens in the 11-02 eval (TTFT median 1.7 s, p90 4.7 s). It works only while
  the rendered prompt is byte-identical up to the new tokens.
- **What breaks the cache** (every one of these was seen in real sessions, 2026-10-27 and 11-04):
  1. The harness rewriting old messages: dsh's tool-result pruner re-wrote old results at 80% context, forcing
     77-98K-token re-prefills (TTFT 344-353 s). Fixed: threshold 16,384 chars, and the `lean` preset for the web UI.
  2. Compaction: the summary replaces history, so the next request is a cold prefill of ~38K tokens. 5 compactions
     took 230-465 s each; one failed at the token cap. Now: thinking off for compaction requests (purpose-effort
     plugin, 2026-11-04; not yet measured live).
  3. Session resume after a server restart without the persistent cache.
  4. A system-prompt change mid-session (plan mode, skills, todo are disabled for this reason).
- **Re-prefill of the model's own previous output** is 38-44% of per-step prefill tokens (~3.5% of agent time):
  Splash keeps a state only at the prompt's replay boundary, so the generated tokens of the last reply are prefilled
  again next step. The park lane (keep the finished lane, adopt it next turn) removes it; it works (4/5 adoptions,
  prompt time −24%) but is **not greedy-identical** on one turn, and is blocked on an oracle test (§11).
- The persistent SSD cache tier matters when free RAM is low (memory note: check `/status` evictions first).

## 7. Where an agent's wall time goes

### 7.1 Measured breakdowns

**Eval baseline 2026-11-02** (t1-t6 × 3, xhigh, before the runaway guard): decode ~93% of agent wall (249K tokens at
54 tok/s), prefill ~5.7%. **66% of all decoded tokens** went into 10 replies that hit the 16,384-token cap while still
thinking and produced nothing; dsh then ended the run (max-tokens finish is sticky; headless exits 1).

**Tree-era real sessions** (25 sessions, 4,750 s): reasoning decode 52.9%, TTFT/prefill 20.6% (7.4 points the pruner
bug), tool execution and approvals 10%, compaction 9.8%, tool-call argument decode 4.7%, answer text 1.8%.

**All 75 dsh sessions to 2026-11-04** (545 steps, 637 tool calls): decode 398 min vs prefill 82 min; 96% of output
characters are reasoning; the slowest 10% of steps are 58% of model time; 13/637 tool-call errors; 9/190 reads
repeated.

### 7.2 What was done about it

| Fix | Effect |
|---|---|
| Runaway guard v2 (plugin): on a max-tokens cut, steer the agent and send the next request with thinking off | eval hidden pass 45% → 85%, wall 275 → 265 s |
| Tool-result pruner threshold 8,192 → 16,384 chars | removed 77-98K re-prefills (−10-14% of long sessions, estimate) |
| Purpose-effort plugin: thinking off for compaction requests only | not yet measured live |
| `lean` preset persona: batch read-only calls, read with offset/limit | not yet measured |

### 7.3 Decisions that stand (the user's)

- **Reasoning stays xhigh** (the template's default; dsh's `reasoning:` setting never reached Splash). Medium was the
  single largest estimated lever (+13-24% agent time) and was declined for quality reasons. Do not re-propose it.
- JEV is off by default (since 2026-10-02).
- The GPU must be fully off when idle: `scripts/stop.sh`, optional `SPLASH_IDLE_STOP`.

## 8. Memory budget

24 GB unified memory, shared with macOS, the IDE and the browser. Splash needs ~16 GiB reclaimable to start.

| Item | Size |
|---|---|
| Target weights (UD-IQ3_XXS) | ~10.7 GB |
| Draft weights | ~1.3 GB |
| KV, turbo-int4, 16.5 KiB/token | 1.6 GB at 100K, 2.4 GB at 150K, 3.3 GB at 208K |
| GDN recurrent state | ~150 MiB per sequence, double-buffered |
| Prefill arena, verify scratch, heads | a few hundred MB (the prefill-arena liveness change saved ~285 MB = +16K context) |

Context is granted in 16K-token steps; the maximum with turbo-int4 is 208,889 tokens (configured 150,000). Anything
that adds memory (a second drafter, a bigger quant) comes out of the context budget or out of what the rest of the
Mac can use. Low free RAM evicts every cached state (the SSD tier then matters).

## 10. How we measure (and why each rule exists)

### 10.1 Environment rules

| Rule | Why |
|---|---|
| AC power only | on battery the Mac is in Low Power mode and the GPU is throttled |
| Record Microsoft Defender's CPU before and after; wait for 30 s of quiet | its real-time scan cost 20-45% of decode speed through memory contention; every new file (builds, caches, the Trash) triggers it |
| Build first, then wait, then time | builds trigger Defender |
| GPU lock (`mkdir /tmp/splash-gpu.lock`) | two GPU jobs at once corrupt both timings |
| A-B-B-A order (or A-B-B-A-A-B across seeds) | cancels thermal and background drift |
| Close Teams/IDE where possible | memory pressure evicts caches |
| decode-profile needs `SPLASH_DRAFT_TREE=1 SPLASH_DRAFT_HEAD_ROWS=98304` (and `DECODE_PROFILE_B1_ONLY=1`) | without them it times the old chain; multi-lane runs throw with the tree |

### 10.2 Exactness classes (what "no accuracy loss" means for each change)

| Class | Definition | Proof required |
|---|---|---|
| **bit-identical** | same bits out of every kernel | exhaustive/unit equality, output digests |
| **exact-math** | same math, different summation order or rounding of intermediate sums | greedy digest equal on a sample, or divergence only at near-ties; fp64 reference tests within tolerance |
| **exact sampling** | different numerics possible, but the sampled distribution equals the target's | design argument (independent uniforms, tree independent of draws) + two-sample distribution tests (dist_test, fruit_test) |
| **approximate** | changes the model's behaviour | the eval gate: t1-t6 × ≥2 reps, hidden-test pass rate within noise of the baseline |

Greedy text can differ under exact-math and exact sampling: a different verify row set reassociates floating-point
sums, and where two tokens nearly tie the argmax flips ("split by" vs "split on"). That is not a bug; a state bug shows
up as incoherent text or a growing divergence, which is what the coherence check after the first differing token is
for.

### 10.3 Measurement tools

| Tool | Measures |
|---|---|
| `decode-profile` (splash-src/dev/benchmarks) | per-dispatch GPU time of one cycle, fused cycle time, greedy digest |
| `decode-run` | end-to-end decode on token-file prompts (greedy or sampled, seeds, `--repeat`), digests per prompt, step log |
| `gguf-projection-benchmark` | one projection shape, every format, split choice, digest mode |
| `kvbench.py` / `run_kv_suite.sh` | the real HTTP server: speed texts, greedy answers, needles |
| `logs/splash/steps.jsonl` + `step_report.py` | every real decode cycle: position, accepted, retained, tree, copy rows, gpu/wall ms |
| `tree_potential.py`, `copy_potential.py` | offline simulation from a draft dump (`SPLASH_DRAFT_DUMP`) or from sessions |
| `eval/run_eval.py` | agent accuracy: t1-t6 hidden tests, wall time, guard continues (`--first-rep` resumes) |

### 10.4 Decision rule used so far

Adopt a speed change when (1) its exactness class is proven, (2) the end-to-end gain beats the run-to-run spread
(every B run beats every A run, or the effect is several times the seed spread), and (3) for anything that changes
outputs or the harness, the eval does not regress. Back up the touched production files to `splash/backups/` first,
then re-export `patches/0003`, then document.

## 12. Adaptation playbook for new technology

The point of this section: given any new paper, repo, model or chip, decide in an hour whether it can help, how much,
and what it would cost, using the numbers above.

### 12.1 First, classify it by which term it moves

| It changes… | Then the questions are… | The ceiling is set by… |
|---|---|---|
| **Tokens per cycle** (drafters, trees, lookup/copy, selectors) | acceptance length on *our* text at T=0.6; does it fit in 16 verify rows; extra draft ms | perfect top-16 selection = 5.91 vs 4.45 tok/cycle (+33%); depth past 7 needs the copy-style commit paths (already built) |
| **ms per cycle, projections** (kernels, quant formats, matmul types) | dequant instructions per weight; does it run on the matrix units; does the format change accuracy | matmul floor ~34 ms (FP16), dequant ~19-23 ms is the movable part |
| **ms per cycle, attention** (KV formats, sparse/selective attention, int8 Q·K) | does it cut attention *math* (not just bytes) at 64-128K | §5.2: compute-bound at 0.25 ms/1K ideal vs 0.34-0.45 measured |
| **Prefill** (caching, chunking, park lane) | does it avoid prefill or make it cheaper; is the prompt still byte-stable | compute peak; 90% cache hit already |
| **Tokens decoded** (reasoning control, guards, compaction, context compression) | effect on the eval pass rate; does it break the prefix cache | the eval gate; user decisions in §7.3 |
| **Memory** (quant, KV format, offload) | what it costs in context length (16.5 KiB/token now) | 24 GB minus ~8 GB for macOS and apps |

### 12.2 The quick estimate

```
new tok/s / old tok/s  =  (new tokens/cycle / old)  ×  (old ms/cycle / new ms/cycle)
agent gain            ≈  decode share (0.6-0.9) × decode gain   (+ prefill share × prefill gain …)
```
Use **our** baselines, not the paper's: tokens/cycle 5.5 short / 4.1-5.0 long; 87 ms + 0.45 ms per 1K context;
decode share ~0.9 in evals, ~0.6 in real sessions with tools and compaction.

Discount published numbers:
- Acceptance-length tables are usually at T=0 on math/code benchmarks; our text is ~96% free-form reasoning at T=0.6.
  Expect a fraction of the gain (the copy extension: +40% synthetic, +16.7% session prompts, +4% real eval).
- "×N faster" claims are usually against no speculation or against a CUDA batch server. Compare against our current
  stack (tree + copy), not against plain decoding.
- Anything measured on CUDA says little about Metal kernel cost; budget a microbenchmark.

### 12.3 Checklist before writing code

1. Which term, which class (bit-identical / exact-math / exact sampling / approximate)?
2. Simulate offline if possible: `SPLASH_DRAFT_DUMP` + `tree_potential.py` for any tree/draft-selection idea;
   `copy_potential.py` for lookup ideas; the step log for context and acceptance distributions.
3. Microbenchmark the kernel in isolation (projection benchmark, decode-profile) before end-to-end.
4. Build in a dev copy (`splash/dev-<name>`, cloned from splash-src), behind an environment switch that defaults off,
   so production stays bit-identical with the switch off.
5. Gate: correctness tests → A-B-B-A on real session prompts → (if outputs or harness change) the eval.
6. Apply: back up, copy, rebuild, re-run the tests on production, re-export patch 0003, document in SPEED_LOG, the
   handoff and this file.

### 12.4 Specific adaptations

**A new drafter** (DSpine, EAGLE-style, Weaver): the target-side machinery (16-row verify, tree mask, tree GDN scan,
exact acceptance, depth-15 commits) is drafter-agnostic. A new drafter must produce, per cycle: candidate tokens per
position with scores the tree builder can use (unary + edge, or a direct tree), and consume the target's captured
hidden rows. Keep DFlash2 selectable (`SPLASH_DRAFTER=dflash2|<new>`); budget its weights against context memory; its
cost per cycle should stay ≤ ~6 ms (DFlash2 today) or pay for itself in tokens/cycle (each +1 ms needs ~+1.2%
tokens/cycle at 87 ms).

**A new target model** (Qwen4, a different hybrid, a MoE): recheck (1) the layer mix (only attention layers pay the
long-context term; a pure-attention model pays it 4× more), (2) GQA ratio and head dim (they set the attention FLOPs
per token, §5.2), (3) whether a trained drafter exists (DFlash/DSpine checkpoints are per target), (4) the quant
formats' dequant cost (§3.2: format barely matters per byte), (5) weights + KV against 24 GB. MoE: decode streams only
active experts, but verify rows with different experts multiply the bytes; the 16-rows-for-free property may not hold.

**A new quantization**: speed per byte is nearly format-independent here (dequant + matmul in series), so judge it
mainly on accuracy and memory. A format the matrix units consume directly (like turbo-int4 for KV) is the exception
that can be faster.

**A new chip** (M5 Max, M6): the projection share scales with matrix-unit throughput, not just bandwidth. Re-run:
the K-split sweep (tiers are per core count, `kStagedTiers` in `runtime/ops/LinearGguf.cpp`), the 16-row tile check,
the int8/e4m3 probe, decode-profile at 2K/32K/64K. More memory changes the menu: a 4-bit target, a bigger drafter,
or two lanes.

**A new Splash upstream release**: our changes are `patches/0003` (engine) and `patches/0004` (lithos). Rebase in a
dev copy, run the unit tests, the decode-run digests with every switch off (must equal the old production), then each
switch's A/B.

**A new harness feature or dsh version**: check that the rendered prompt stays byte-stable (cache hits), that plugins
using `agent/turn-stopping`, `agent/request` and `agent/assistant-stream` still receive the same payloads (runaway,
purpose-effort), and rerun the eval.

## 13. External techniques evaluated

Full reports: [EXTERNAL-2026-11-09.md](EXTERNAL-2026-11-09.md). Earlier external reviews (Weaver, Graft,
SuffixDecoding, EAGLE-3, Quest, MLX, llama.cpp) are in RESEARCH-ADVANCED-2026-11-02.md §2.5 and §4.

| Technique | Term it moves | Our estimate | Status |
|---|---|---|---|
| **Tencent DSpine** (drafter with a Qwen3.8-27B checkpoint; block-causal, predecessor injection, 16×16 refined tables) | tokens/cycle | +3-10% decode (central +5%); the "4×" is vs no speculation on CUDA; vs DFlash2 their own table says +8-21% with block 16 vs 8, and +4-10% at equal block | promising; offline kill test first (§12.4 applies: same interface, tree/copy/shortlist kept) |
| **billion-context** (model-written context folds via a proxy + dsh plugin) | context length → ms/cycle and prefill | ~20-25% only in sessions past ~50K, if a 3-bit 27B folds reliably (their pilot: 5/8 succeeded) | not adopted; the no-code control `DSH_SHORT_CONTEXT=1` added instead |
| **codebase-memory-mcp** (DeusData: code knowledge graph over MCP, `--tool-profile=scout`) | fewer steps and reads → context and decode | up to the ~89% of tool-result chars that are code navigation, if the 27B adopts it; scout schema costs ~2.3K tokens of context (~1% decode) on every request | opt-in trial planned (EXTERNAL section 3.4); needs a download (ask) |
| Weaver / DFlash-TfM (learned selector over DFlash top-K) | tokens/cycle | up to +32% claimed; needs training we can't do locally | watch for a released 27B adapter |
| Graft / token recycling | tokens/cycle | +1-3% on top of copy | overlaps the copy extension |
| Quest-style page selection | attention ms | +11-27% at 58-131K | approximate; last resort |

Lessons that generalize: published speedups are almost always against plain decoding and at T=0 on math/code; a
drafter's gain shrinks once a tree and context copying are already in place; and model-driven context management
needs a model that reliably follows tool doctrine, which a 3-bit 27B often doesn't.

## 15. Glossary

- **Anchor**: the last committed token; a cycle drafts after it.
- **Cycle**: one draft + verify + accept + commit; emits accepted tokens + 1.
- **DFlash2**: the block drafter (proposes 7 tokens in parallel from target hidden states).
- **GDN (Gated DeltaNet)**: the linear-attention recurrent layers (48 of 64).
- **Staged tile**: the projection kernel shape: dequantize a weight tile into threadgroup memory, then a matrix
  multiply on the matrix units.
- **K-split**: splitting a projection's input dimension across threadgroups, then summing partials.
- **Tree / copy rows**: verify rows beyond the chain: alternative candidates (tree) and context-copied tokens (copy).
- **Exact sampling**: speculative decoding whose output distribution equals the target's own.
- **turbo-int4**: the KV format (Hadamard rotation + int4).
- **TTFT**: time to first token (mostly prefill).
- **Runaway reply**: a reply that hits the 16,384-token output cap while still thinking.
