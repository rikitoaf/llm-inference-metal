## Item 2 — faster prefill at long context (largest engine lever)  [2026-11-18: PROCEED, narrowed to the attention kernel: 53% of a 100K chunk at ~16 TFLOP/s; chunk 4096 dropped (−0.5..−1.8%)]
**Why:** at 100K, every agent step pays 5–21 s to process its new tokens before the first output token. The fit
says half of a prefill token's cost at 100K is attention over the cached context (2.45 ms flat + 2.45 ms at 100K).

**Steps:**
1. **Profile first (one GPU run, ~15 min):** prefill a 2K-token chunk at positions 20K, 60K and 100K. Split the time
   into projections, GDN, and attention per attention layer (16 layers), and note the attention kernel's achieved
   TFLOP/s and bandwidth. Tools: `splash/tools/attn_perf`, the attention profile from HANDOFF-SPEED-2026-10-28.md.
   Output: `splash/dev-prefill/PREFILL.md` table. **Decide from this table**: if attention is under 30% at 100K,
   stop item 2 and move its time to items 3 and 6.
2. **Candidates, in order of expected value per day:**
   a. **Tile shape for long prefill attention:** the current kernel was tuned for prefill at short positions (the
      2026-10-21 prefill-arena work). Larger KV tiles and more query rows per threadgroup at ≥40K, with turbo-int4 K
      fed straight to `matmul2d` (no dequant loop), as the verify kernel already does. Bit-identical or exact-math.
   b. **Split-K over the context for long positions:** parallelise one chunk's attention over KV ranges and merge
      (log-sum-exp), as verify attention already does with its split grid. Exact-math.
   c. **Chunk size at long context:** 2048-row chunks; test 4096 at ≥60K (fewer passes over the KV cache per new token).
      Exact-math (the same summation-order class as today's chunking, measured by the park oracle's two-chunk control).
   d. **Skip prefill of the model's own reply:** already done by the park lane; extend adoption so it survives host
      memory pressure (3 of 6 park A/B arms lost the lane on some turns at 0–0.5 GiB headroom).
3. **Correctness gate:** cold prefill logits against the current engine for every candidate (max abs diff within
   the two-chunk control, same argmax), greedy digests or near-tie only, dist/fruit tests.
4. **Speed gate:** `splash/tools/prefill_ab.sh` (new): TTFT of 2K/4K suffixes at 30K/60K/100K, A-B-B-A, plus
   `park_long.py` turns. Ship if TTFT at ≥60K improves ≥10% with no correctness flag.

**Expected:** −20–30% prefill time at 100K, about −10–15% model time in long sessions.

## Item 3 — fewer steps per task
**Why:** each step costs a prefill of its new tokens plus a reasoning preamble; most steps make one call.
CBM already cut steps 40% on cross-repo tasks, but cost time on single lookups (large results).

**Steps:**
1. **Measure the changes already made** (batching rule, `limit: 10`, search_code hints) with the platform bench:
   `python3 workspace/platform-bench/run_bench.py --serve --label steps-1 --reps 1` (all 22 tasks). Metrics:
   steps/task, calls/step, graph share, wall, score. Compare to 20.5 / 12.4 steps and 332 s.
2. **Parallel graph calls:** check that dsh runs MCP calls of one step in parallel (if it serialises them, batching
   saves model time but not tool time; then make the graph calls a single batched tool or raise dsh's MCP
   concurrency).
3. **Smaller graph answers by default:** a thin proxy in front of codebase-memory-mcp (like
   scripts/xerj-mcp-filter.mjs) that sets `limit: 10` when absent, drops JSON-schema `Variable` noise from
   search results (20K of 27K nodes in one repo), and shortens the long qualified names in output (the model passes
   them back verbatim, so keep a lookup map in the proxy). Target: −50% graph result chars on single lookups.
4. **Step-shape nudge at the tool level:** when a step makes one read-only call and the previous step did too,
   the graph-first reminder plugin adds a one-line "batch the next lookups" note (same mechanism as the drift
   reminder; stored in the session, cache-safe).
5. **Gate:** platform bench steps/task −20% vs step 1 with score not lower, single-lookup tasks not slower than
   the no-graph baseline (spi-02 61 s, spi-05 136 s).

**Expected:** −15–25% wall on multi-step tasks.

## Item 6 — cheaper DSpine draft at long context  [DROPPED 2026-11-18: draft = 9% of a 112 ms cycle at 103K; 8-row draft saves 1.6 ms but costs 9% tok/cycle (profile-1)]
**Why:** the DSpine draft costs +4.8 ms per cycle at long context (about 4–5% of a 102–109 ms cycle), part of it
16-row attention over its 8192-token window and the bridge.

**Steps:**
1. **Profile the draft (same GPU run as item 2 step 1):** ms for backbone layers, window attention, bridge
   (dense bf16 matmuls), refinement gather, tree build.
2. **Candidates:**
   a. Draft only the rows the verify policy keeps: above 64K only 8 rows are verified, so the draft's rows 8–15 (and
      the refinement tail for depths ≥ 8) are wasted work. Cut them when the policy is active. Exact (the tree's
      first 8 rows are unchanged).
   b. Bridge weights in Q8 (memory and bandwidth), gated on golden tolerance and acceptance.
   c. Fuse the bridge's small kernels (code, gate, message, write) into one dispatch.
3. **Gate:** draft ms −30% at ≥64K, tok/cycle unchanged within noise (A-B-B-A, 2 seeds, 70K and 103K prompts),
   golden and distribution tests pass.

**Expected:** −2–4% per cycle at long context (a is nearly free).

## Item 7 — fewer aborted turns (accuracy)
**Why:** 14 of 28 turns were aborted; transcripts show the agent editing when the user asked for analysis or a
narrower change, and long deliberation before acting.

**Steps:**
1. **Classify the 14 aborted turns** from the session files (CPU): over-reach (edited without being asked), wrong
   direction, too slow, or the user changed their mind. Output a table in `workspace/platform-bench/ABORTS.md`
   (local; company content stays out of the repo).
2. **Plan-before-edit rule** for change requests: when a request is ambiguous about scope ("look at", "analyse",
   "can you", "why"), answer or propose a short plan and stop; edit only after an explicit "do it/implement/fix".
   Delivered through the per-turn reminder plugin (it already runs at step 1 of each user turn), not the system
   prompt.
3. **Scope check before the first edit in a turn:** the reminder plugin adds one line when the first `edit`/`write`
   of a turn comes before any user message containing an action verb (cheap heuristic; logged, measurable).
4. **Bench additions:** 4 new platform-bench tasks that are analysis-only ("explain why…", no edits expected) and
   2 narrow-change tasks; the grader fails a run that edits in an analysis task or touches files outside the asked
   scope.
5. **Gate:** no regression on the existing 22 tasks; 0 unwanted edits on the 4 analysis tasks; then watch the
   abort rate in real sessions (target: under 25% of turns).
